# Known limitations

Plain statements of what Mummer does **not** do or has **not** verified. The product copy repeats the user-relevant ones.

## Product and privacy

1. **The draw is run by the host's browser (trusted-host).** A host can see or record pairings. Not host-blind. (F14 not built.)
2. **No independent payment proof.** "Sent" and "received" are self-reports. Mummer cannot inspect a shielded payment and has no viewing key. (F15 not built.)
3. **No company-funded mode.** Zodl iOS rejects multi-recipient requests; a funding design needs its own privacy review. (F13 not built.)
4. **Small groups leak by deduction.** Four people can narrow the cycle; five or more is recommended.
5. **A giver knows their recipient** and a recipient may infer their giver from timing, amount or a note.
6. **Address substitution by a malicious operator or database writer** is possible because sealed boxes are anonymous. Two checks narrow it but do not close it: (a) each join sends a hash (the "address commitment") of the nickname and address, which the host's browser re-checks against the opened profile and the giver's browser re-checks against the roster before showing a payment request, so a swap of the profile *alone* is caught (but the commitment is a public hash with no member signature behind it, so someone who can write to the database can replace a profile and its commitment together without detection); (b) the host's invite link carries a fingerprint of the host's public key, so joiners notice a swapped host key. An operator who serves altered JavaScript can defeat both, and a joiner who opens an invite without the fingerprint gets only a notice. Ask recipients to confirm arrival.
6a. **Redraw griefing.** The draw is pinned to a "members version" so a join or leave between reading and drawing makes the draw fail rather than silently omit someone. A member who repeatedly joins and leaves can therefore make a host retry. Rate limits bound this; it is not eliminated.
6b. **Sealed-blob sizes are now constant (fixed 4096-byte plaintext envelope).** Until 28 October 2026 they were bucketed in 256-byte steps, which let a database observer match givers to recipients by comparing bundle and profile lengths (a critical finding of an independent audit, fixed and verified on the deployed instances; see `docs/PRIVACY_RELEASE_AUDIT.md`). The server now refuses any other length (HTTP 422, "out of date, reload"), so a page that was open before the fix cannot store old-size data. Exchanges created before the fix cannot be completed with the new client, which cannot open old-size blobs; they must be deleted and recreated, and nothing can make an old exposure secret again. Production had no such exchange with members when this was deployed.
6c. **The host-plays option** means the host's own assignment is produced by the same browser that knows every pairing. The interface says so.
7. **Network metadata** (IP, timing) is visible to hosting and network providers; platform log retention was not inspected.
8. **Public counts** are rounded and thresholded, but counters are not differentially private.
8a. **The host's "glass box" shows totals** (for example how many have confirmed), never which person has or has not, because that per-person state would let a host narrow who is giving to whom.

## Zcash and wallets

9. **No real wallet was tested.** Whether Zodl iOS or Android fills in the amount and memo from a scanned Mummer QR is unverified (R01/R02, R12). No wallet can run in the development environment (no Windows build of Zodl; no emulator tooling or virtualization). A person can do the scan test in 10 to 15 minutes with no money: `docs/ZODL_MANUAL_TEST.md`. What exists instead: Mummer's payment requests are accepted and decoded identically by the **reference Rust `zip321` parser** (`npm run test:crosscheck`), which shows another implementation of the specification agrees, **not** that Zodl does. **No Zcash testnet transaction has been made**: the toolchain download was done, but building `zcash-devtool` was blocked by the harness's permission policy and nothing was retried by another route (`docs/INTEGRATION_RESEARCH.md`). The UI always offers copy buttons and never claims a scan prefilled anything.
10. **Receivers are validated structurally** (checksum, lengths, ordering), not for curve-point validity.
11. A unified address that also contains a transparent receiver is accepted with a warning.
12. **Mainnet only.** Test-network addresses are refused everywhere.
13. **Exchange rate** comes from two public sources tried in order, CoinGecko then Kraken (CoinGecko answers HTTP 403 to Cloudflare Workers, found on the first deployment), cached for 60 seconds; quotes are approximate and expire after ten minutes. If both fail, no request is shown and the copy buttons remain. Neither source is cross-checked against the other.

## Platform and operations

14. **Deployed on the free tier, but production has never had a real exchange created on it.** https://mummer.mummer-app.workers.dev (with the separate check host https://mummer-check.mummer-app.workers.dev) is live and passes the read-only live checks, but creating or joining needs a person to pass Cloudflare's real Turnstile challenge, which an automated browser cannot, so that last step is a **manual step** (`docs/DEPLOYMENT.md`). The complete journey was verified on a **staging** deployment that uses Cloudflare's public test keys. Reveal day cannot be tested on any live deployment (the clock cannot be moved).
15. **Turnstile:** the first design (an opaque-origin sandboxed frame) does not work against Cloudflare and was replaced by a separate-origin check host (decision D-37). On production the real widget renders inside that frame and an always-pass control delivers a token with the verified origin, but the **real managed challenge has not been completed** by anyone. Until a person does it once on production, that path is unproven in the field.
16. **No independent security review**, no penetration test, no formal verification.
17. **Rate limiting relies on `CF-Connecting-IP`**, which is trustworthy only behind Cloudflare.
18. **Local storage** keeps a person's key and token on their device for convenience; "Forget this device" removes it, together with any pending link replacement and local reveal guesses. A link that carries a *different* key than the one saved is never applied silently: the person chooses.
19. **Timezone handling** uses the platform's Intl data; exotic historical zone changes are not special-cased.

## Product scope

20. No native app, no email, no push notifications, no calendar file (F16 optional, not built), no languages other than English, no dark theme.
21. Real-money trial with 4 to 5 consenting people (R12): **not done**. No usage figures or user counts are claimed anywhere.

## Accessibility

22. **Accessibility:** automated checks (axe-core, WCAG 2.2 AA tags) and keyboard tests pass for every route and key state at 390 and 1280 px in Chromium, Firefox and WebKit; **no screen reader has been used** (`docs/ACCESSIBILITY_MANUAL_CHECKLIST.md` lists what a person must verify). Treat WCAG conformance as *targeted and automatically checked*, not certified. Safari reaches links only with Option+Tab, which automation cannot press, so the WebKit skip-link test checks document order and focus instead.
23. **Test-infrastructure failure under load (cause established; one original occurrence not proven identical).** One security test once received an HTTP 500 from a join request in one of seven full runs. Diagnostics added to the error handler then captured the same failure under deliberately heavy load: `TypeError: fetch failed` with underlying cause `connect EADDRINUSE 127.0.0.1:<port>`. The integration harness reaches Miniflare's real D1 over a loopback connection; a full suite opens about 4,000 short-lived connections, each lingering in TIME_WAIT for two minutes on Windows, whose dynamic range is 16,384 ports (13,933 were in TIME_WAIT when it failed). This is a limit of the **test environment**, not of the deployed Worker, which reaches D1 through Cloudflare's binding. A guard in the test harness (`workers/api/test/resilient-d1.ts`) now retries only a connect that failed with EADDRINUSE or EADDRNOTAVAIL (nothing was sent, so a repeat cannot duplicate a write), logs each retry, and never retries anything else. Four consecutive full runs afterwards: 0 retries needed, 0 server errors, all passing. The very first occurrence had no diagnostics, so it is consistent with this cause but **not proven** to be it. Running several full suites in parallel on this machine is not supported: it produces timeouts and `ECONNRESET` failures that the guard deliberately does not retry.
24. **Browser coverage:** Chromium is the reference run: the whole suite passed in one command (76 of 76). Firefox and WebKit pass the join, validation, recovery, storage-failure, accessibility and browser-security specs (including the new cross-origin frame tests), WebKit also the link-replacement and review-fix specs, and the full 12-viewport responsive matrix ran once in each (WebKit 12 of 12; Firefox 11 of 12, the failure being a measurement artifact since corrected) with the narrowest and landscape viewports rerun under the stricter audit; runs were made spec by spec, not as one combined run (`docs/EVIDENCE.md`). **The six-participant journey fails in WebKit**, at a different step each run. During a run this machine had about 0.26 to 0.4 GB of its 7.8 GB RAM free while WebKit used about 0.6 GB, and every shorter WebKit spec passes, which is consistent with memory starvation, but that is a correlation, not a diagnosis. No real iOS Safari, Android Chrome or other devices were used.
25. **Workers free-tier budget.** With `run_worker_first = true` every page and asset request is a Worker request (and the check host is a second Worker), so each is assumed to count against the free plan's 100,000 requests per day for the whole account (the documentation does not state this outright). Fine for small exchanges; revisit before wide promotion.
26. **Workers Logs** are configured off for all four Workers and the Cloudflare API shows no observability block, Logpush off and no tail consumers; that is consistent with logging being off but is not an explicit confirmation, so check the dashboard. Whether invocation logs would include client IPs, and Cloudflare's edge retention, are unverified.
27. **Storage failures:** blocked, full or failing browser storage is covered for opening a link, restoring, and replacing a link. The "keep or use the other link" conflict screen when the chosen link then cannot be stored is implemented (held in memory, fragment kept) but has no automated test, because the situation needs two valid keys and failing writes at once.

## Open items from the 28 October source reviews (not fixed before submission)

Found by two independent reviews on 28 October 2026 (`docs/BUILD_REVIEW_2026-10-28.md`, plus the re-audit). The 46 to 50 person draw failure (high) and several wording issues are fixed. Still open:

- Joining while the browser blocks site storage loses the credentials on "Go to my page" (the saved link still recovers the account).
- Three concurrency windows inferred from the code, not reproduced: a post-draw removal racing the host closing the exchange; a reveal racing a removal; the lazy deadline lock racing a deadline extension. Each needs an exact interleaving and is unlikely at small-group scale.
- "Forget this device" can fail silently when browser storage is full.
- Comment and lint-directive clean-ups.
- The six requested viewport sizes, a full keyboard and screen-reader pass, wallet acceptance and production CAPTCHA completion by an auditor were not tested.
